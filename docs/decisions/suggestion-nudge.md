# 제안 표현 방식

## Decisions

- 서비스가 먼저 꺼내는 모든 제안(아침 안내, 저녁 안내, 길찾기, 주변 명소, 여비 기록 권유처럼 사용자가 묻지 않았는데 보여 주는 것)은 노선도 바로 아래로 내려오는 알약 모양 섬으로 보여 준다. 화면 전체를 덮거나 본문 자리를 차지하는 카드로 먼저 띄우지 않는다.
- 섬은 테마 주 색 계열의 은은한 그라데이션과 반투명(뒤 화면이 비치는 흐림 효과)을 쓰고, 흐릿하게 내려오며 나타난다. 왼쪽에 숨 쉬듯 빛나는 점이 있다.
- 접힌 상태는 질문으로 끝나는 한 줄과 오른쪽의 짧은 정보 한 개(예: "🚇 약 12분", "☀️ 1일차")만 보여 준다. 누르면 같은 섬이 아래로 펼쳐져 자세한 내용과 버튼이 나온다.
- 펼친 섬의 버튼은 실행(주 버튼, 예: "길 보여줘")과 미루기(예: "나중에") 두 개가 기본이다. 실행은 사용자가 주 버튼을 눌렀을 때만 일어난다.
- 한 번에 섬은 하나만 보인다. 사용자가 실행하거나 미룬 제안은 같은 상황에서 다시 뜨지 않고, 이 기록은 계정에 저장되어 기기를 바꿔도 같다.
- 승인된 모양은 `docs/specs/osaka-contextual-suggestions/prototype.html`의 섬이 기준이다.

## Boundaries

- 사용자가 직접 연 화면의 본문(코스 목록, 체크리스트, 여비 목록)은 섬으로 바꾸지 않는다. 섬은 서비스가 먼저 묻는 것에만 쓴다.
- 앱이 닫혀 있을 때의 푸시 알림 모양은 이 결정에 포함되지 않는다.
- 어떤 상황에서 어떤 제안을 띄울지(시점, 거리, 빈도)는 각 작업 단위의 사양서가 정한다. 이 결정은 보여 주는 방식만 정한다.

## Why

첫 버전의 아침·저녁 안내는 정해진 시각에 고정된 자리에 카드가 먼저 떴다. 사용자는 이것이 챙겨 주는 친구라기보다 공지문처럼 느껴진다고 했고, 필요한 순간에 생각이 떠오르듯 알림처럼 뜨고 사용자가 원할 때만 진행되기를 원했다(2026-11-19). 같은 상황(1일차 14:30, 다음 장소 출발 30분 전)으로 아래 말풍선, 노선도 아래 섬, 노선도 아래 옅은 한 줄을 비교했고, 사용자는 섬 모양에 옅은 한 줄의 그라데이션과 반투명을 더하고 질문으로 끝나는 문장과 현재 위치 기준 소요 시간을 넣는 안을 골랐다.

## Reconsider when

- 섬이 노선도나 화면 위쪽의 주요 동작을 가려서 쓰기 불편하다는 근거가 실제 사용에서 나올 때
- 푸시 알림이 들어와 앱 밖과 안의 제안 모양을 맞춰야 할 때
- 한 번에 하나만 보여 주는 규칙 때문에 중요한 제안이 늦게 보인다는 근거가 나올 때

## Still-rejected alternatives

- 화면 아래 말풍선이 떠올랐다가 반응이 없으면 작은 점으로 접히는 방식 — 엄지가 닿기 쉽지만 사용자가 섬 모양을 골랐다. 위쪽이 붐빈다는 근거가 나오면 다시 검토한다.
- 노선도 아래의 옅은 한 줄 — 가장 조용하지만 놓치기 쉬워서, 테마(그라데이션·반투명)만 가져왔다.
- 화면을 차지하는 안내 카드를 먼저 보여 주는 방식(첫 버전) — 고정된 공지처럼 느껴진다.
