# 사용자 데이터 저장

## Decisions

- 여행, 체크리스트, 여비 같은 사용자 데이터는 로그인한 계정에 묶어 Supabase Cloud의 Postgres에 저장한다. 브라우저 저장소를 원본 저장소로 쓰지 않는다.
- 로그인은 Supabase Auth의 이메일/비밀번호로 시작한다. 연결과 인증 구성은 로컬 스킬 `setup-supabase`의 방식을 따른다.
- 사용자가 올리는 파일(서류 사진, PDF 등)은 Supabase Storage의 비공개 버킷에 계정별 폴더로 저장하고, 그 계정만 올리고 읽고 지울 수 있게 한다. 파일을 열 때는 짧게 유효한 서명 링크를 쓴다. 파일의 이름, 종류, 어느 여행에 속하는지 같은 정보는 Postgres 행에 따로 둔다.

## Boundaries

- 데이터 접근은 행 소유자만 허용하는 것으로 시작한다. 동반자 공유는 이 결정이 허용하지 않으며, 초대 기능을 설계할 때 따로 정한다.
- Google 로그인은 이 결정에 포함되지 않는다. 나중에 Google 쪽 설정과 함께 추가한다.
- 파일 저장 규칙은 공개 링크로 파일을 나누는 기능을 허용하지 않는다. 동반자와 파일을 나누는 일은 초대 기능을 설계할 때 함께 정한다.

## Why

`PRODUCT.md`의 동반자 초대와 일정 공유에는 계정과 서버 저장이 반드시 필요하다. 첫 작업부터 브라우저에 저장하면 나중에 저장 방식을 바꾸고 데이터를 옮기는 일을 한 번 더 해야 한다. 사용자는 Supabase 계정을 이미 갖고 있고, 저장소에는 연결 절차를 담은 `setup-supabase` 스킬이 있다.

파일은 여권 사본처럼 민감한 것이 많아서 주소만 알면 열리는 공개 버킷은 맞지 않는다. Postgres 행에 파일을 직접 넣으면 권한은 기존 RLS로 끝나지만 DB가 빠르게 커지고 큰 PDF에 맞지 않는다(사용자 확정, 2026-11-19).

## Reconsider when

- 동반자 공유를 설계하면서 Supabase의 권한 모델(RLS)로 공유 범위를 표현하지 못한다는 근거가 나올 때
- 오프라인 사용이 제품의 핵심 요구로 확정될 때

## Still-rejected alternatives

- 로그인 없이 브라우저에만 저장 — 사전 준비 없이 바로 써 볼 수 있지만, 기기 간 이어 보기와 동반자 공유가 불가능하고 나중에 이전 작업이 생긴다. 제품에서 공유가 빠지면 다시 검토한다.
- 공개 Storage 버킷 — 가장 쉽지만 파일 주소를 아는 누구나 열 수 있어 여권 사본에 맞지 않는다. 민감하지 않은 공개 이미지(예: 명소 사진)만 다룰 때 다시 검토한다.
- 파일을 Postgres 행에 직접 저장 — 권한 처리는 단순하지만 DB 용량과 큰 파일 전송에 맞지 않는다. 다시 검토할 조건은 없다.
